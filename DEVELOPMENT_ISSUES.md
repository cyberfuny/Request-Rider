# Проблеми розробки та рішення

Цей файл фіксує проблеми, що виникали під час розробки та QA
RequestRider, щоб подальша робота розпочиналася з уже відомих причин і
рішень.

## 1. Перехід із попереднього TypeScript-програми на Django та Go

### Симптом

У робочому дереві одночасно перебував старий стек TypeScript/Node.js та
нова реалізація на Django та Go. Старі frontend/server-файли більше не
відповідали поточний архітектурі.

### Причина

Проєкт перенесено на розділену схему:

```text
Browser -> Django :8000 -> Go engine :8081
                         -> passive proxy :8080
```

### Рішення

- старі TypeScript entrypoints видалено з актуальної версії;
- Django став browser-facing gateway і власником SQLite History;
- Go став execution engine, Intruder runner і passive MITM proxy;
- README і Prompt оновлено відповідно до нової структури;
- основні межі шарів зафіксовано на карті проєкту.

## 2. У Traffic відображалися лише завершені запити

### Симптом

Запит ставав видимим у UI лише після отримання відповіді. Це створювало
відчуття затримки й не давало змоги спостерігати повільні або ще виконувані
запити.

### Причина

Proxy додавав подію до Store лише всередині callback відповіді.

### Рішення

Життєвий цикл події розділено на дві фазі:

1. під час вхідного запиту створюється підія зі статусом `pending`;
2. після відповіді та сама підія оновлюється: стан, тіло, розмір, error і latency.

У події з’явився стабільний `id`, тому UI може замінити pending-запис
оновленою версією.

## 3. Traffic оновлювався лише після ручного Refresh

### Симптом

Нові proxy-запити не з’являлися в інтерфейсі автоматично.

### Причина

UI використовував лише періодичне/ручне отримання snapshot через
`GET /api/traffic`.

### Рішення

Додано SSE-потік:

```text
Go Store -> /events/stream -> Django /api/traffic/stream -> EventSource
```

Snapshot використовується для початкового завантаження, SSE — для наступних
оновлень запитів/відповідей.

## 4. SSE-події затримувалися в Django gateway

### Симптом

Go одразу надсилав невелику SSE-подію, але браузер отримував її із затримкою.

### Причина

Django gateway читав upstream-потік блоками по 4096 байт. Невеликі події
залишалися у внутрішньому буфері, доки не накопичувався достатній обсяг.

### Рішення

Читання змінено на `readline()`, щоб кожен рядок SSE передавався одразу.
Після цього перевірка в реальному часі через proxy почала проходити без затримки.

## 5. Proxy показував сертифікат `goproxy.github.io`

### Симптом

Firefox показував:

```text
MOZILLA_PKIX_ERROR_MITM_DETECTED
```

і повідомляв, що сертифікат випущено `goproxy.github.io`.

### Причина

У старій версії під час локального запуску engine без `CA_DIR` GoProxy використовував
вбудований CA замість сертифіката проєкту з `data/ca`.

### Рішення

- локальний CA `data/ca/ca.crt` додано до профілю Firefox NSS;
- engine перезапущено з `CA_DIR=/home/kali/my_intruder/data/ca`;
- у `main.go` додано автоматичне виявлення `data/ca` і `../data/ca`;
- README доповнено інструкцією щодо CA.

Тепер сертифікати MITM підписуються:

```text
Local HTTP Lab Root CA
```

Поточна поведінка: `ConfigureCA()` автоматично обирає `data/ca` або
`../data/ca`, створює `ca.crt` і `ca.key` під час першого запуску та записує активні
шляхи в журнал. Для запуску без ручного `export` доступний `./run-engine.sh`.

## 6. Docker proxy слухав лише loopback усередині контейнера

### Симптом

Порт proxy було опубліковано через Docker Compose, але контейнер не приймав зовнішні
підключення через опублікованою адресою.

### Причина

Go engine типово слухав `127.0.0.1`, що усередині контейнера означає
лише loopback самого контейнера.

### Рішення

Додані змінні:

```text
PROXY_LISTEN_ADDR=0.0.0.0:8080
ENGINE_LISTEN_ADDR=0.0.0.0:8081
```

Вони використовуються у Docker Compose, а локальний запуск зберігає loopback
defaults.

## 7. Запуск сервісів із неправильного каталогу

### Симптом

Команди `go run .` і `python manage.py runserver` завершувалися помилками
`go.mod file not found` і `manage.py not found`.

### Причина

Команди виконувалися із `/home/kali`, хоча вихідні файли розташовані в:

```text
/home/kali/my_intruder/engine
/home/kali/my_intruder/web
```

### Рішення

В інструкціях запуску явно вказано `cd engine` і `cd web`. Під час автоматичного
запуску використовуються абсолютні робочі каталоги.

## 8. Повторний запуск завершувався `port already in use`

### Симптом

Повторний старт engine або Django завершувався помилкою зайнятого порту.

### Причина

Попередні процеси вже продовжували працювати:

```text
8000  Django
8080  proxy
8081  engine
```

### Рішення

Перед повторним запуском перевіряються health endpoints і HTTP-відповіді. Якщо
сервіс уже доступний, новий екземпляр не запускається.

## 9. Двійкові відповіді через Repeater відображаються як текст

### Симптом

Під час запиту PNG через Repeater у JSON body з’являлися символи заміни UTF-8.

### Причина

Engine повертає тіло відповіді у JSON-рядку, а двійкові байти не є
коректним UTF-8 текстом.

### Поточний стан

HTTP-запит виконується коректно, розмір і статус відповіді зберігаються.
Для повноцінної робвіди з двійковими відповідями наступна версія має додати
режим base64 або окрему download/export відповідь.

## 10. Live Passive Store працює у пам’яті

### Симптом

Незбережені Traffic passive proxy events очищуються після перезапуску engine.

### Причина

Store реалізован як in-memory структура Go для швидкого пвідоку в реальному часі.
Автоматичне збереження кожної події не виконується.

### Рішення і поточний стан

У Traffic додано кнопку `Save`. Вона надсилає подію до
`POST /api/traffic/save`, після чого запит/відповідь зберігається у SQLite
History з джерелом `proxy`. Незбережена live event і надалі залишається
у пам’яті engine, а збережена запис переживає перезапуск сервісів.

## 11. Оновлення інтерфейсу під raw HTTP workflow

### Вимога

Класичний набір розрізнених полів був незручним для аналізу повного
HTTP exchange і не відповідав цільовому split-pane workflow.

### Рішення

- Repeater отримав окремі raw Request/Response панелі;
- raw запит розбирається у наявний structured контракт Django без нового
  backend API;
- відповідь відображається одним повним raw HTTP представленням і не змінює
  збережені байти;
- двійкові відповіді доступні у Base64-представленні з початковим MIME type;
- History і Traffic використовують верхній inspector з окремою прокручуваною
  таблицею пакетів для повного запит/відповідь;
- Intruder отримав єдіній raw запит editor, маркери додаються виділенням
  тексту, а target/режим/transformations розташовані на правій панелі;
- результати Intruder показуються компактною таблицею з повними inspector
  панелями запит/відповідь;
- CSS залишається локальним і self-contained, тому запуск проєкту не пвідребує
  Node/Tailwind toolchain.

### Обмеження

Raw editor зараз є textarea, а не Monaco Editor. Це зроблено навмисно:
поточний проєкт не має frontend-збірки, а textarea зберігає нульові runtime
залежності і сумісність з локальним Django запуском. Monaco можна додати
пізніше окремим frontend build етапом без зміні Go/Django API.

## 13. Мінімалістичний workflow і очищення live Traffic

### Вимога

Після перевірки інтерфейсу було видалено дубльовані controls, які не
використовуються у робочому процесі: structured fields і capture controls
Repeater, імпорт History, ручне оновлення live Traffic і зайві відповідь
формати.

### Рішення

- Repeater працює лише через єдиний raw HTTP запит editor;
- Intruder використовує той самий підхід, з marker selection у повному запити;
- History містить лише Repeater і Intruder records;
- Traffic отримує пакети автоматично через SSE;
- `Refresh traffic` очищає поточний in-memory snapshot і replay backlog,
  після чого нові події знову надходять через SSE;
- `Clear history` видаляє лише записи Repeater/Intruder;
- History import видалено із UI;
- верхній inspector History/Traffic відокремлено від прокручіваемого списку пакетов;
- повні запит/відповідь зберігаються й відображаються без обрізання.

### Перевірка

Зміни перевірялися inline JavaScript syntax check, Django check,
Django tests, Go tests і `git diff --check`.

## 14. Затримки під час великого Intruder-словнику через logging

### Симптом

Під час запуску Intruder з великим словником кулери голосно працювали, а інтерфейс
починав сильно гальмувати.

### Причина

Go engine записував у журнал окремі повідомлення для кожного Intruder job:
`job_start`, `job_complete` і `job_error`. Під час тисячах payloads це створювало
великий пвідок виводу у термінал і на диск.

### Рішення

Логування кожного job вимкнено. Виконання запитів, worker pool,
live-результати, polling і відображення UI не змінюються. У журналах залишаються
агреговані lifecycle-повідомлення атаки і помилки верхнього рівня.

## 15. URL-фазінг з ffuf-подібними маркерамі

### Вимога

Для перебору сегментів URL потрібен маркер, який можна записувати у звичному
вигляді `%payload%`, наприклад `/api/%payload%/`.

### Рішення

Engine і UI підтримують три синтаксиси маркерів: `§name§`, `{{name}}` і
`%name%`. Останній замінюється до створення вихідного HTTP-запиту, тому
сирий URL з `%payload%` не передається у `net/http` як незавершений escape.
Наявні Intruder режими і transformations застосовуються без змін.

## 16. Відновлення Intruder після перезавантаження сторінки

### Симптом

Перезавантаження сторінки мігло перервати відображення активної атаки або запускати
автоматичне скасування, хоча engine продовжував або мав продовжувати надсилання
запитів.

### Причина

Життєвий цикл browser UI був помилково пов’язаний з `pagehide`: обробник
відправлял `DELETE` під час reload, закритті вкладки або навігації. Крім того,
без збереженого ідентифікатора новий екземпляр сторінки не мог під’єднатися к
вже запущенной атаки.

### Рішення

- активний `attack_id` зберігається у `localStorage` за ключем
  `intruder-lab-active-attack`;
- після завантаження сторінки збережена атака відновлюється, і polling
  продовжує отримувати її стан і нові результати;
- `pagehide` більше не викликає скасування;
- `Cancel attack` і `Clear результати` є єдиними діями UI,
  які надсилають `DELETE /api/intruder`;
- після `completed` або `cancelled` збережений ідентифікатор видаляється;
- результати, вже збережені під час атаки, залишаються у History.

Такім образом, reload змінює лише стан UI, а не стан engine.
Завершення атаки пвідребує явного дії користувача.

## 19. Затримки за великих Intruder-словниках

### Симптом

За великої кількості payloads інтерфейс переставав відповідати, а термінал
отримував величезний потік журналів.

### Виправлення

- engine використовує bounded worker pool замість goroutine на кожен job;
- per-job журнали вимкнено, залишено aggregate lifecycle/error logs;
- результати передаються порціями через `since` і `limit`;
- UI зберігає лише обмежене видиме вікно рядків у DOM;
- `delay_ms` дає змогу запускати запити послідовно з паузой;
- збережена Intruder-конфігурація включає delay.

Ці зміні зменшують навантаження на Go engine, gateway і browser rendering,
не відкидаючи результати із History або Traffic.

## 20. Target site map

Додано вкладка Target і API асинхронного crawler:

```text
POST   /api/target-map
GET    /api/target-map?map_id=<id>
DELETE /api/target-map?map_id=<id>
```

Краулер підтримує `max_pages`, `max_depth`, `delay_ms` і `same_origin`.
Він аналізує HTML links/forms, script і stylesheet references, URL-шляхи у
JS/CSS/JSON, `robots.txt`, `sitemap.xml`, `Sitemap:` directives і XML `<loc>`.
Кожен ресурс отримує depth, стан, URL, Content-Type і kind.

Стан карти зберігається у пам’яті engine і зникає після його перезапуску.
Результати не додаються автоматично у History/Traffic, но доступні у UI
для експорту JSON, CSV і текстового дерева.

## 21. Межа статичного і browser-driven обходу

Target навмисно виконує звичайні HTTP GET-запити і не виконує JavaScript,
не змінює DOM після script execution і не надсилає форми. Тому дінамічні
маршрути, доступні лише після кліка або submit, поки не видно. Для цього
потрібен окрему Chromium/Playwright worker, якій планується як наступний
етап і не має змішуватися з легким статичним crawler.

## 17. Повні результати Intruder і проізводітельность великих атак

### Симптом

За великих словників браузер міг зависати, а таблиця показувала загальний
`PENDING` або `ERROR` замість фактичного HTTP-стану і відповідь.

### Причина

UI повторно завантажував і перемальовував весь масив результатів, а engine створював
надто багато goroutines для кожного job. Gateway також зберігав результати
лише після фінального стану атаки.

### Рішення

- engine використовує worker pool і context cancellation;
- GET `/api/intruder` піддержівает `since`, повертаючи лише нові результати і
  `result_offset`;
- UI накопичує результати по cursor і не створює DOM для вже відображених
  рядків повторно;
- Django зберігає результати у History під час виконання атаки і
  дедуплікує їх по `proxy_session` і `proxy_event_id`;
- відповідь з `400`, `403`, `404`, `500` і іншими HTTP-кодамі відображається як
  звичайний результат зі станом, заголовками і тілом;
- `error` без HTTP стан залишається зарезервованим для network/TLS/reset і
  інших випадків, коли сервер не повернув відповідь;
- Traffic і History не відримують штучного ліміта у 1000 записів.
  Traffic залишається live до явного `Refresh traffic`, а History зберігає
  отримані Intruder exchange у SQLite.

Це зберігає повноту HTTP-аналізу і одночасно зменшує обсяг повторної
передачі JSON і DOM-операцій у браузері.

## 18. 403 під час очищення Traffic

### Симптом

Після натискання `Refresh traffic` UI отримував HTML-відповідь Django `403 Forbidden`
замість успішного очищення live Traffic.

### Причина

`DELETE /api/traffic` проходив через CSRF middleware, але browser fetch не
передавав CSRF token для цього локального API-дії.

### Рішення

Traffic DELETE позначено `csrf_exempt`. Gateway і надалі явно обробляє
помилки engine, а очищення видаляє лише in-memory snapshot і replay backlog
Traffic; SQLite History не змінюється.
